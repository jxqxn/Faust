# 《风花雪月》校园循环与《苏丹的游戏》基座对照

> 状态：已讨论并由用户确认的设计研究结论。
>
> 记录日期：2026-08-10
>
> 用途：确认《苏丹的游戏》已经具备哪些《风花雪月》式人物日程骨架、哪些结构仍需改造，以及一项可验证的决策面压缩候选架构。
>
> 证据边界：原作仪式配置与反编译代码用于确认《苏丹的游戏》的对象、槽位和结算行为；关于怎样改造 Faust 的部分属于项目设计判断，不是原作事实。

> 可复现配置统计、校园日程资料与项目数据缺口见[游戏设计数据研究总报告](../research/faust-game-design-data-research.md)中的 `SG-CFG-001`、`FE3H-RULE-001`、`FE3H-EXPL-001`、`FAUST-DES-001` 与 `FAUST-DATA-001`。本文的改造优先级是项目决策，不是外部数据直接推出的最优解。

## 1. 明确结论

《苏丹的游戏》已经具备《风花雪月》校园玩法最难复制的核心：持续人物、人物调度、行动占用和后果回写。它缺少的不是“校园内容”，而是《风花雪月》用来压缩、组织这些内容的稳定节奏，以及让玩家主动塑造人物的清晰培养路径。

两者的共同本质是：

> 玩家怎样分配人物，就是这些人物的经历怎样形成。

最值得继承的组合不是“在《苏丹的游戏》之外另建一套修道院”，而是：

> 用《风花雪月》的节奏与信息压缩，组织《苏丹的游戏》更直接、更具后果的人物仪式叙事。

## 2. 已经同构的骨架

| 《风花雪月》 | 《苏丹的游戏》 | 共同本质 |
|---|---|---|
| 固定学级与学生名册 | 持续存在的人物卡 | 玩家长期管理同一批具名人物 |
| 安排教学、小组任务、出战 | 把人物放入不同仪式槽位 | 决定谁在这段时间做什么 |
| 学生参加一项活动，不能同时参加另一项 | 进入进行中仪式的人物被该仪式占用 | 人物是有限、互斥的行动资源 |
| 教学与活动改变技能、职业和支援 | 仪式修改人物标签、品级、装备、关系与状态 | 行动结果回写同一人物 |
| 支援关系改变人物演出和相邻作战收益 | 人物身份与关系标签改变仪式分支 | 关系不仅是文本，也是规则条件 |
| 培养结果在月底战斗中兑现 | 人物状态被后续仪式和事件继续读取 | 过去选择改变未来选择 |
| 经典模式永久死亡 | `clean` 等结果永久移除人物 | 角色损失具有不可逆性 |

《苏丹的游戏》的运行时 `Rite` 对象保存 `cards`、`start`、`start_round` 和 `life`，配置 `RiteNode` 保存 `round_number`、`auto_begin`、`auto_result` 与槽位定义，说明仪式并非只有一次静态文本，而是能够持有人物、进入进行状态并在后续结算的运行时对象。

结构定位：`dump.cs:392391`（`Rite`）、`dump.cs:393154`（`RiteNode`）。

## 3. 《苏丹的游戏》更直接的地方：仪式本身就是人物故事

《风花雪月》通常把关系活动、培养和战斗验收分成连续环节：

```text
与英谷莉特吃饭
→ 恢复动机
→ 下周指导飞行
→ 成为天马骑士
→ 在战斗中兑现
```

《苏丹的游戏》的仪式往往把人物活动与故事结算合并在同一次槽位选择里。

### 3.1 浴场约会

`data/config/rite/5001503.json` 的“浴场约会”要求投入具体妻子与主角，并允许选择是否投入纵欲或杀戮苏丹卡：

- 普通约会会为槽位中的妻子增加“激情”；
- 使用纵欲卡的匹配分支可以增加“激情”和“支持”；
- 使用杀戮卡则执行 `clean.s1`，直接清除这名妻子。

同一槽位投放同时回答策略与人物问题：什么对象满足条件，以及玩家是否愿意这样对待这个具体的人。

### 3.2 残忍的牺牲

`data/config/rite/5000004.json` 要求投入杀戮苏丹卡、主角和一个符合品级的具体追随者。结算根据妻子、伊曼、拜铃耶等人物身份与状态选择不同文本、计数器、生成物和后续事件，但最终操作的仍是槽位中的具体人物。

反编译代码确认统一的对象回写链：

- 结算面板依次检查条件并返回匹配的普通结算分支：`[SRC: decompiled/RiteResultPanelController.c @ GetNormalSettlement (RVA 0x5A32B0, dump.cs:325592)]`
- 标签操作通过 `OperationFilter.Filter` 取得具体对象再执行修改：`[SRC: decompiled/DesktopModifyTag.c @ DoTemplate (RVA 0x50E400, dump.cs:314136)]`
- 清除操作同样通过过滤器收集对象并执行移除回调：`[SRC: decompiled/DesktopCleanCard.c @ DoTemplate (RVA 0x4F8250, dump.cs:313733)]`

因此，改造时不能把仪式退化为纯粹增加经验的课程菜单。仪式最重要的优势是：人物亲自参与事件并承担具体后果。

## 4. 最大差异：被组织的学期与不断扩张的事件网络

《风花雪月》每个月用一个中心问题过滤全部校园活动：

> 月底有这场任务，我准备怎样的学生去应对？

吃饭、教学、目标、小组任务、职业考试和辅助战斗虽然很多，但都能被“是否有助于月底任务和长期培养”筛选。

《苏丹的游戏》则可能同时要求玩家处理苏丹卡、人物支线、常驻行动、装备与标签匹配、多个进行中仪式、期限和路线断点。它的问题不是缺乏关联，而是关联持续增长，却没有稳定的中心将它们压缩为少量当前选择：

```text
《风花雪月》
一个月底目标
→ 数周准备
→ 一次集中验收

《苏丹的游戏》
多个仪式不断出现
→ 多条期限与人物链并行增长
→ 各自在不同时间结算
```

这也解释了为什么《苏丹的游戏》后期容易从“选择让谁承担后果”变成“搜索哪张卡符合哪个槽位”。有意义状态的增长速度超过了界面的信息压缩和自动化能力。

## 5. 需要改进的四个方面

### 5.1 手牌不应等于全部人物名册

降低手牌数量不等于删除人物或长期状态，而是区分四种不同职责：

- **人物名册**：所有持续存在的人物；
- **当前手牌**：本周期真正可能投入的少量人物与对象；
- **进行中区域**：已经被安排、正在行动的人物；
- **关系与历史**：由系统保存，需要时查询，不持续占据操作平面。

原则是：

> 名册可以很大，但当前决策面必须很小。

这也延续《酒馆战棋》对手牌、战场和外部机会的区分：区域不是自由库存分页，而是对象处于不同承诺状态的规则表达。

### 5.2 需要能够过滤当前选择的周期中心问题

Faust 不必照搬月份、星期或苏丹卡倒计时，但每个阶段需要一个明确问题：

- 本周期要完成什么；
- 哪些人物和对象与它相关；
- 玩家有多少次主动安排机会；
- 最后通过什么结果检验安排。

题材可以是考试、社团比赛、校园危机或集体行动。作用不是制造另一种期限压力，而是把庞大世界状态过滤成少量相关选择。

### 5.3 人物成长需要允许玩家先形成培养意图

《苏丹的游戏》的人物会通过标签、品级、装备、计数器和事件链持续变化，但许多方向只有结算后或查阅攻略才能理解。这有利于发现与意外，却不够支持《风花雪月》式的培养作者感。

学生需要一种玩家可理解的长期方向，使玩家能够表达：

> 我希望这个人逐渐成为怎样的人，或者在集体中承担怎样的角色。

这不等于复制职业树。玩家提出培养意图，仪式负责实际塑造；人物性格、关系和遭遇仍可使结果偏离计划。这样既保留作者性，也承认人物不是完全服从的技能胚子。

### 5.4 已经解决的日常行为需要自动推进

《风花雪月》让玩家设置目标并重点指导少数学生，普通工作日自动推进。《苏丹的游戏》中已经形成稳定答案的日常行为仍可能要求反复找仪式、找人物、拖入、开始并观看相似结算。

应保留第一次建立方案时的判断，但允许稳定安排转化为：

- 默认执行者；
- 自动填入；
- 快速结算；
- 只在风险、人物状态或结果变化时重新请求决定。

玩家负责改变安排，不必每天证明自己仍记得原来的安排。

## 6. 一项优先级较高的候选改动

相较于增加课程、职业或校园小游戏，可以优先验证：

> 当前周期目标—有限活跃手牌—进行中人物

其结构为：

```text
完整人物名册
    ↓ 根据当前周期目标筛选
少量活跃手牌
    ↓ 玩家投入仪式
进行中人物
    ↓ 结算
人物成长、关系变化与未来事件
```

这一改动同时解决两件事：

1. 像《风花雪月》一样，让玩家知道这一阶段为什么培养和安排人物；
2. 降低《苏丹的游戏》中后期所有卡牌与仪式同时争夺注意力的问题。

它不破坏《苏丹的游戏》的宿主语法：人物仍是卡牌，玩家仍把卡投入仪式，仪式仍按具体对象选择分支，结算仍回写或清除同一人物。变化只在于，不相关的全部世界状态不再同时占据当前手牌。

## 7. 明确保留与禁止误改

### 必须保留

- 卡牌作为可调度世界对象；
- 把卡放入仪式槽的核心交互；
- 同一人物实例贯穿关系、行动、成长、战斗与存档；
- 人物身份和关系参与结算分支；
- 选择能够永久改变或终结人物未来；
- 仪式本身可以是剧情，而不只是训练容器。

### 不应照搬

- 不复制修道院地图和小游戏清单；
- 不把月份、星期或行动点 UI 当作创新本体；
- 不另建一套与卡牌、槽位和结算互不相干的校园菜单；
- 不完整保留原作全部管理负担后再叠加课程、商店、阵容和自走棋库存；
- 不以删除人物长期状态的方式实现“少手牌”。

## 8. 事实、观察与设计推论

### 原作验证事实

- 运行时仪式与静态配置分离；运行时 `Rite` 保存具体卡牌和进行状态。
- 普通结算会根据当前上下文选择匹配分支。
- 标签修改与清除操作能够通过过滤器作用于具体卡牌对象。

### 配置观察

- `5001503` 会根据妻子、主角及可选苏丹卡修改或清除具体妻子。
- `5000004` 会根据投入追随者的身份和状态选择不同人物文本与后续操作。

### 项目设计推论

- 《苏丹的游戏》已经具有《风花雪月》式名册调度与持续后果骨架。
- 其主要缺口是稳定节奏、有限活跃决策面和可预期的培养方向。
- “当前周期目标—有限活跃手牌—进行中人物”是用于压缩决策面的优先候选之一，不是已经批准的最终规则或实现方案；其讨论顺序可以随用户指导、新证据和原型发现调整。
