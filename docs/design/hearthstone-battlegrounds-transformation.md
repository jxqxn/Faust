# 《酒馆战棋》如何用《炉石传说》语法完成自走棋化

> 状态：设计研究基线（2026-08-10）
>
> 用途：解释《酒馆战棋》如何通过高比例复用《炉石传说》的对象、表现、规则语言与产品入口，只集中改写少数高杠杆控制流，形成自走棋体验；并据此约束 Faust 对《苏丹的游戏》底座的改造方法。
>
> 关联研究：[`fire-emblem-narrative-transformation.md`](fire-emblem-narrative-transformation.md)、[`sultans-game-narrative-transformation.md`](sultans-game-narrative-transformation.md)、[`sultans-game-cognitive-load-and-automation.md`](sultans-game-cognitive-load-and-automation.md)、[`mahjong-autobattler-common-origin.md`](mahjong-autobattler-common-origin.md)

## 1. 核心结论

《酒馆战棋》的低成本并不是“没有开发一套新游戏”，而是：

> 保留《炉石传说》的对象、语言与操作手感，只改写少数决定游戏类型的控制流程。

它保留英雄、英雄技能、随从、手牌、七格随从区、攻击与生命、种族、关键词、卡牌拖放、战斗动画和客户端入口，却重新规定了：

- 随从从哪里获得；
- 玩家在什么时候决策；
- 随从是否跨回合持续存在；
- 攻击由玩家还是系统执行；
- 玩家面对一个还是多个对手；
- 失败按一次输赢还是按多人名次衡量。

因此，它的方法可以概括为：

> 复用名词，改写动词；复用表现，改写循环。

这使它在内容资产、玩家学习、产品分发和原型验证上成本较低，却仍然获得了与经典对战完全不同的体验。

但“低成本”不能被误解为整体工程量很小。将原本以 1 对 1 为前提的《炉石传说》改造成稳定的八人对局，是需要服务器、客户端及多个职能共同完成的大型工程。正确判断是：

> 《酒馆战棋》以极高的复用率，把有限的新增投入集中在八人控制流、持续阵容与自动战斗等真正创造新体验的边界上。

## 2. 被复用的宿主语法

| 《炉石传说》既有要素 | 《酒馆战棋》中的新职能 |
|---|---|
| 英雄 | 一局游戏的统帅与流派倾向 |
| 英雄技能 | 改变招募、经营或战斗策略的局内规则 |
| 随从卡 | 自走棋单位 |
| 手牌 | 已购买随从及奖励牌的临时中转区 |
| 七格随从区 | 阵容容量与站位空间 |
| 攻击力、生命值 | 自动战斗的基础数值 |
| 种族 | 阵容协同和构筑方向 |
| 战吼、亡语、嘲讽、圣盾等 | 自动战斗的组合语言 |
| 金色卡牌的既有表现 | 三张同名随从合成升级的反馈形式 |
| 费用资源的界面语言 | 酒馆金币经济 |
| 卡牌拖放与战斗演出 | 购买、出售、布阵和战斗反馈 |
| 炉石客户端及账号体系 | 免费入口、匹配、社交和既有用户分发 |

暴雪在首发介绍中直接把该模式描述为：玩家熟悉的随从类型、关键词与卡牌，以从未体验过的方式进行游戏。首发模式直接进入《炉石传说》客户端，公开测试阶段对所有炉石账号开放。

来源：[暴雪官方《Introducing Hearthstone Battlegrounds》](https://news.blizzard.com/en-us/article/23156373/introducing-hearthstone-battlegrounds)

内容生产也采用了高复用策略。开发者在 BlizzCon 2019 访谈中表示，首发约 90 张随从里有 10 张是专门为酒馆战棋全新设计的独占卡牌。其余内容并非原样复制，而是从已有内容中筛选适合新控制流的对象，再进行模式专属平衡。

来源：[BlizzCon 2019《炉石传说》团队访谈](https://game.udn.com/game/story/10453/4141931)

## 3. 少数但高杠杆的控制流替换

经典对战的基础循环是：

```text
预先组牌
→ 每回合抽牌
→ 获得法力
→ 玩家出牌并手动攻击
→ 一名玩家获胜
```

酒馆战棋的基础循环是：

```text
选择英雄
→ 酒馆随机提供随从
→ 购买、出售、刷新、升级与调整顺序
→ 自动战斗
→ 承受伤害
→ 回到酒馆继续改造持续阵容
→ 八人淘汰至最后一人
```

它没有逐项增加大量新规则，而是替换了少数系统枢纽：

| 经典对战 | 酒馆战棋 | 类型变化 |
|---|---|---|
| 对局前构筑固定牌组 | 对局中根据随机供给构筑 | 从执行预案转为临场适应 |
| 双方交替回合 | 招募阶段与自动战斗阶段交替 | 决策和执行被分离 |
| 玩家指定攻击对象 | 系统按顺序、嘲讽和随机目标执行 | 微操转为阵容与顺序设计 |
| 棋盘状态不断交换、消耗 | 阵容跨战斗轮次持续成长 | 单局内部形成长期培养 |
| 法力用于打出不同费用卡牌 | 金币用于购买、刷新和升级 | 资源竞争集中到经营取舍 |
| 1 对 1 的单次胜负 | 八人淘汰和名次结算 | 失败具有多个中间层级 |
| 卡组决定主要组合空间 | 当前可得随从决定组合空间 | 适应能力替代完全预设 |

## 4. 它如何压缩自走棋的认知负担

《酒馆战棋》没有完整照搬《刀塔自走棋》的二维棋盘、移动距离、装备栏、物品栏、利息经济和备战区。

开发者明确表示，模式中的互动和机制尽量来自卡牌本身，并且有意不设置物品栏与装备栏，使玩法相对单纯。金币不能跨回合保存；购买、刷新和升级直接争夺同一回合的有限资源，玩家不需要长期计算利息并等待收入增长。

来源：[BlizzCon 2019《炉石传说》团队访谈](https://game.udn.com/game/story/10453/4141931)

这种简化没有消灭策略，而是重新分配策略：

- 二维空间被压缩成七格左右顺序；
- 装备构筑被压缩进随从自身文字与增益；
- 长期存钱被压缩成当前回合购买、刷新和升级的竞争；
- 手动攻击被压缩成战前排列和效果组合；
- 连续微操被压缩成离散的招募决策窗口。

七格顺序尤其关键。左侧随从先攻击、嘲讽改变目标、亡语要求考虑死亡顺序、召唤效果要求预留空位。它用一维事件顺序替代二维棋盘，显著降低空间管理量，同时保留足够的组合深度。

## 5. 自动战斗的真正作用

自动战斗不是单纯减少操作，也不是用动画代替玩法。它承担三项职能：

1. **接管低层执行**：玩家不必逐次选择普通攻击；
2. **验证高层设计**：阵容、顺序、升级和协同在战斗中接受检验；
3. **汇总复杂结果**：大量数值与关键词交互被转化为一次可观察的系统报告。

因此，玩家的职责从“逐个命令单位”转成：

> 设计一个系统，然后观察这个系统怎样运行；再根据结果修改设计。

这不是取消玩家能动性，而是把能动性从执行层上移到构筑、取舍、预测和调整层。

## 6. 为什么随机供给能够提高耐玩度

经典构筑的主要计划在对局前完成；随机酒馆则让构筑成为对局本身。

开发者强调，组合依然重要，但玩家不应从开局就机械追逐某个必胜组合；重点是运用当下真正能够招募的随从。由此，每局会自然形成一条适应过程：

```text
我原本想构筑什么
→ 当前资源允许我构筑什么
→ 我是否继续投入、暂时过渡或彻底转型
```

来源：[BlizzCon 2019《炉石传说》团队访谈](https://game.udn.com/game/story/10453/4141931)

随机性的作用不是替玩家决定结果，而是持续向玩家提供不完全相同的问题。高手优势主要表现为识别当前资源的用途、衡量转型成本和及时放弃已经失效的预案。

### 6.1 成型是成长引擎的启动点

《酒馆战棋》中，找到核心单位或凑齐关键组合通常不表示阵容已经完成。争夺第一的阵容往往还需要把后续每一轮的金币、随从、法术和战斗触发转化为永久属性、经济或召唤能力。

官方卡池长期反复使用“永久获得属性”“本局持续增强”“每回合继续成长”和“保留战斗增益”等设计。因此，许多阵容的核心不是七个最终单位，而是一台能够继续接收资源并提高产出效率的增长引擎。

来源：

- [暴雪 26.6 补丁中的永久成长设计](https://hearthstone.blizzard.com/en-gb/news/23973115/26-6-patch-notes)
- [暴雪卡牌库：塔蕾苟萨保留战斗增益](https://hearthstone.blizzard.com/en-us/battlegrounds/72062-tarecgosa?tier=3&type=minion)

这使玩家不仅比较当前战力，也比较：

- 谁更早启动成长核心；
- 谁能以更高效率把当轮资源变成下一轮强度；
- 谁能在牺牲即时战力追求成长时保存足够生命；
- 谁能在终局用圣盾、烈毒、亡语、攻击顺序等结构越过单纯数值。

所以不能把酒馆战棋简化成纯粹的大数字竞赛。更准确的结构是：即时战力决定能否活到引擎启动，成长速度决定长期上限，终局针对防止结果完全退化成数值比较。

这与四川麻将“血流成河”的相似之处，不是二者采用同一种数值成长，而是都让首次成型成为持续运转的开始：酒馆阵容继续成长，成型牌型继续接受牌流并反复结算。完整证据边界见 [`mahjong-autobattler-common-origin.md`](mahjong-autobattler-common-origin.md)。

## 7. 为什么八人排名减轻了竞争挫败

经典对战只有赢或输；酒馆战棋用第一至第八名表达表现，通常进入前四便能提升评分。

开发者认为，八人淘汰制与大逃杀游戏具有相似的心理结构：玩家并不预期自己每局都必须获得第一；如果早早淘汰，可以立即重新排队。第一名仍然提供强烈成功感，而普通失败不像 1 对 1 落败那样具有完全否定性。

来源：[Game Developer 对 Dean Ayala 与 Melissa Corning 的访谈](https://www.gamedeveloper.com/design/why-the-i-hearthstone-i-devs-wanted-to-make-an-auto-battler)

这种结构为竞争结果增加了中间状态：

- 第一名是完整胜利；
- 前四是局部成功；
- 后四仍然提供关于阵容和经济决策的可调整反馈；
- 早期淘汰不会迫使玩家继续完成已经失去悬念的长局。

## 8. 成本判断的证据边界

### 8.1 确实被降低的成本

- 插画、音效、动画和卡牌表现资产；
- 随从属性、种族与关键词的基础设计；
- 卡牌显示、拖放和战斗反馈等客户端交互；
- 玩家理解符号与规则词汇的学习成本；
- 新产品的下载、账号和用户获取成本；
- 用已有逻辑快速建立内部可玩原型的成本。

### 8.2 没有被消除的成本

- 从 1 对 1 扩展到稳定八人对局的服务器与客户端架构；
- 八名玩家并行触发大量攻击、效果和动画时的性能与内存问题；
- 模式专属随从池的筛选、平衡和长期维护；
- 持续阵容、随机配对、断线重连、排名与淘汰流程；
- 与经典对战不同的交互边界，例如自由调整随从顺序。

开发者称最初的八人玩法原型可以供设计师试玩，却不具备稳定公开发布的工程质量；正式投入后需要服务器团队和多个职能共同参与。另一场访谈记载，从想法形成到公布大约开发了六个月，并把八人同场对弈称为“一大工程”。

来源：

- [Game Developer 开发过程访谈](https://www.gamedeveloper.com/design/why-the-i-hearthstone-i-devs-wanted-to-make-an-auto-battler)
- [BlizzCon 2019《炉石传说》团队访谈](https://game.udn.com/game/story/10453/4141931)
- [暴雪官方首发说明中的移动设备性能限制](https://news.blizzard.com/en-us/article/23156373/introducing-hearthstone-battlegrounds)

因此，不得从本研究得出“依托旧项目的新模式天然便宜”这一结论。真正可以复用的是经过验证的对象、表现和交互；宿主系统原本不存在的控制流仍然必须按新功能开发和验证。

## 9. 成功原因

《酒馆战棋》的成功来自多项优势叠加：

1. **进入门槛低**：无需预先组牌，且公开测试对炉石账号免费开放；
2. **规则识字复用**：熟悉英雄、随从、种族和关键词的玩家可以迅速开始；
3. **决策集中**：玩家在招募阶段作出少量高层选择，系统接管连续执行；
4. **随机问题生成**：随机供给迫使玩家适应，而不是完整照抄固定牌表；
5. **反馈清晰且适合观看**：自动战斗把构筑结果集中表现出来；
6. **失败心理成本较低**：八人名次提供第一名之外的中间成功；
7. **既有生态分发**：模式直接进入原客户端，能够触达已有用户与内容创作者；
8. **内部原型已验证强循环**：团队内部测试时出现员工大量占用午休和工作前后时间继续游玩的现象。

上线后的参与度也支持这种判断。动视暴雪在 2020 年第三季度财报中称，《炉石传说》游玩时长同比增长，酒馆战棋自上一年 11 月发布以来持续保持强劲参与度，并将其视为炉石通过新模式提高参与度的证明。

来源：[动视暴雪 2020 年第三季度财报](https://investor.activision.com/node/33741)

## 10. 对 Faust 的约束性启示

本研究不支持直接复制酒馆、三合一、八人吃鸡、种族羁绊或同一套 UI。应当复制的是改造方法：

> 把新类型真正需要的职能映射到宿主系统已经成立的对象上，只为无法由宿主承担的关键控制流增加新系统。

初步映射如下：

| 自走棋职能 | Faust 中可以承担该职能的既有对象 |
|---|---|
| 持续成长的单位 | 具名、可死亡、具有 UID 与持续状态的人物卡 |
| 阵容 | 当前共同参与行动的人物及其关系 |
| 协同 | 人物关系、身份、观念和共同经历标签 |
| 配置空间 | 手牌、仪式槽及其投放语法 |
| 自动执行 | 仪式启动后的行动与连续结算 |
| 单位成长 | 同一人物实例的能力、关系、伤害和意志变化 |
| 随机供给 | 校园环境在当前阶段提供的人物、机会和问题 |
| 结果反馈 | 行动产生的剧情、状态变化和永久后果 |

后续设计必须遵守以下原则：

1. **保留宿主语法，而不是另做一套自走棋界面。** 手牌、卡牌流转、仪式槽、人物实例和结算反馈应继续承担主要交互职能。
2. **自动化必须替换旧负担。** 如果在原有大量手牌、仪式、期限和搜索操作之外，再增加商店刷新、装备、合成和站位管理，认知负担只会继续上升。
3. **玩家保留高层人物选择。** 系统可以代替玩家检索、重复执行和微观结算，但不能替玩家决定牺牲谁、信任谁、培养谁或让谁承担后果。
4. **自动行动必须反馈既有培养。** 玩家应能从行动结果中看出人物能力、关系、观念和此前经历如何发挥作用。
5. **结果必须回写同一人物。** 对局或行动不能成为无后果的小玩法；成长、伤害、关系和死亡要继续改变校园生活及后续选择。
6. **限制活跃决策面。** 不要求玩家同时理解全部卡牌和仪式，而是在每个决策窗口压缩出少量真正不同的行动方案。
7. **优先改控制流，不机械复制表层机制。** 是否需要商店、合成、名次或多人淘汰，必须由本项目的问题决定，不能因为它们属于酒馆战棋就默认采用。
8. **区分首次成型与真正结束。** 后续研究应确认 Faust 中什么结构会在首次成型后继续存在，以及它如何把新的输入转化成成长、收益与风险；这不等于预先批准持续阵容或持续仪式。

## 11. 后续原型的检验问题

1. 玩家能否沿用对手牌、拖放和仪式槽的已有理解开始游戏？
2. 新增规则是否集中在少数真正改变体验的控制流，而不是建立平行系统？
3. 自动结算是否减少了检索、重复确认和微观执行？
4. 每次要求玩家停下来时，选择是否具有阵容、人物或关系上的长期意义？
5. 玩家能否从演出中理解自己的配置为什么成功或失败？
6. 活跃人物和行动方案是否受到清晰容量限制？
7. 同一人物是否跨行动持续成长并承担后果？
8. 即使移除酒馆、三合一和种族羁绊等表层符号，核心循环是否仍然成立？

最终原则是：

> 《酒馆战棋》没有靠增加更多系统完成创新，而是让《炉石传说》已有对象进入一种新的生命周期，并让阵容首次成型后继续成长和接受检验。Faust 的自走棋化同样应当让既有卡牌、人物和仪式进入新的决策与结算循环，而不是在它们旁边搭建另一款游戏。
